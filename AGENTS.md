# AGENTS.md

Orientation for automated agents (Claude Code, Codex, Copilot) working in this repo. It records how the repo is built and which patterns are deliberate, so automated reviewers do not re-raise settled decisions. Human-first orientation, the repo map and the launch status live in `CLAUDE.md`; read that first.

## Stack

Single-package npm project at the root (no workspaces). React 19.3, Vite 8, TypeScript 6.0, Tailwind CSS 4 via `@tailwindcss/vite`, Lucide React (two icons), `@fontsource-variable/bricolage-grotesque` (self-hosted brand font). Tests are Vitest 5 + React Testing Library + user-event on jsdom 30. ESLint 10 flat config in `eslint.config.js`. Dependabot keeps versions current in weekly (site, GitHub Actions) and monthly (`infra/`) grouped PRs (`.github/dependabot.yml`); security updates open at any time, through the repository's Dependabot security updates setting (`infra/README.md` step 0.3).

CI pins Node 24 (`node-version: '24'`); `.nvmrc` says `24.20.0`. `engines` is `^22.22.2 || ^24.15.0 || >=26.0.0`, jsdom 30's floor copied wholesale (it excludes Node 23 and 25, and is not an intent to run Node 26).

No animation library (no Framer Motion). The design has no entrance animations, and such libraries render their initial state as inline `style="opacity:0..."` attributes, which the prerender would bake into the served HTML and the production CSP would block.

`infra/` is a second, separate npm package; see **Infra package** below.

## Commands

`CLAUDE.md` (Key commands) has the ones you need daily, including the `infra/` checks. The rest:

```bash
npm run type-check   # tsc --noEmit only
npm run lint:fix     # eslint . --fix
npm run test:watch   # vitest
npm run lighthouse   # lhci autorun (uploads reports to temporary public storage; locally prefer `npx lhci collect && npx lhci assert`)
```

## Build and test facts

- Vitest is configured in the `test` block of `vite.config.ts`; there is no root `vitest.config.ts`. It collects only `src/**/*.test.{ts,tsx}`, so `infra/`'s suites never run under jsdom. Globals are off, so `src/__tests__/setup.ts` registers jest-dom matchers, calls Testing Library's `cleanup` after each test, sets `IS_REACT_ACT_ENVIRONMENT`, and stubs `window.matchMedia`.
- Tests read files from `process.cwd()` (the repo root), never `import.meta.url`, which is not a file URL under jsdom.
- `deploy-workflow.test.ts` reads `.github/workflows/deploy.yml` and `ci.yml` as text, with no YAML parser and no build: the prune's exclude list must equal the upload's, each filled by the exact `read -r -a PAGES <<< "$PAGE_KEYS"` line and `for key in "${PAGES[@]}"` loop, with only the pinned run-time check of the list (every key in `$PAGE_KEYS` excluded by name, or the step fails) between it and the sync; both syncs must end with `"${EXCLUDES[@]}"` (continuations joined, so a misspelled or dropped array, or a missing backslash, fails), the prune's sync must be the upload's plus `--delete`, and `--delete` must appear once, after the invalidation. Do not propose a YAML parser for this: what it checks is shell inside `run: |` blocks, which a parser returns as one opaque string. The test does not replace a shell linter; actionlint (which runs shellcheck on `run:` scripts) is not in CI, and adding it is a separate decision, not a fix for this test.
- CI's `check` job starts by failing a PR that changes a file in `public/` in place (`git diff --diff-filter=M` against `main`, the three metadata files excepted): the deploy caches those files as immutable for a year, so a changed file gets a new name (`-v2`). Its checkout fetches two commits for that.
- `dist-html.test.ts`, `hydration.test.tsx`, `contact-prehydration.test.tsx`, `route-manifest.test.ts` and `csp-compat.test.ts` read the build output; run `npm run build` first. They fail with that instruction rather than skipping.
- Pre-commit: `.husky/pre-commit` runs `npx lint-staged` (`eslint --fix` on staged `*.{ts,tsx}`). Type errors surface at `npm run build`.
- `scripts/prerender.mjs` is self-asserting and fails the build on: a route without exactly one `<h1>` matching `ROUTES[].h1`, a head tag that is missing or duplicated in the template, a canonical or hreflang link surviving into the noindex 404, a missing font file, or a route the deploy manifest cannot express.
- The root ESLint run ignores `infra/` (`eslint.config.js`), and the root `tsconfig.json` includes only `src` (and `vite-env.d.ts`).

## Infra package (`infra/`)

- A standalone npm package, `osep-website-infra`, with its own `package.json` and `package-lock.json`. The root scripts never reach it; run everything from inside `infra/`. CommonJS, because `cdk.json` runs the app through ts-node; nothing is compiled to disk (`npm run build` is `tsc --noEmit`).
- `aws-cdk-lib` is pinned exactly (2.273.0, a bump is always deliberate); the `aws-cdk` CLI is a caret range resolved in the lockfile. They move together: the CLI must read the cloud-assembly schema the library writes. Also `constructs` 10, `cdk-nag` 3, TypeScript 5.x (ts-node does not run on TypeScript 7), `@types/node` 24, Vitest 5.
- `npm test` is `vitest run` (`test/**/*.test.ts`: the stacks' templates, the canonical-host function, the DNS records, the settings, cdk-nag) followed by `node --test test/*.node-test.mjs` (the contact Lambda, no npm dependencies, a fake `sendEmail`). The Lambda tests read `src/lib/contactForm.ts` and `src/content/copy.ts` and fail if limits, the email pattern, payload keys or English labels drift from the form.
- `lambda/contact-form/` deploys as plain source with no bundling and no `node_modules`: `index.mjs` wires SES v2 (`@aws-sdk/client-sesv2`, which the Lambda runtime provides) into `createHandler()` from the pure `contact.mjs`. Node 24 (`NODEJS_24_X`), arm64.
- `functions/canonical-host.js` is CloudFront Functions code (`cloudfront-js-2.0`: ES5 style, `var`, 10 KB limit). Synth replaces `__CANONICAL_HOST__` in it with `primaryDomain`.
- Region is always `us-east-1` (CloudFront certificates and SES). The account is never in code: it comes from the `--profile` a human passes (`CDK_DEFAULT_ACCOUNT`).
- Settings are `cdk.json` context keys (`primaryDomain`, `apexDomain`, `dnsProvider`, `contactToAddress`, `contactFromAddress`, `githubRepo`, `wafRateLimit`, `contactRateLimit`), validated by `lib/config.ts`, whose `DEFAULT_CONTEXT` a test holds equal to `cdk.json` except for the two launch decisions, `dnsProvider` and `githubRepo`, which `cdk.json` records once people decide them and which need only be valid there.
- cdk-nag's AWS Solutions checks run inside every synth (`bin/osep-website.ts`), so a finding stops `synth`, `diff` and `deploy` alike. A finding is fixed, or acknowledged next to its resource with a specific reason; `test/nag.test.ts` fails on an unacknowledged finding and on an acknowledgment that no longer suppresses anything. Two remain: CFR1 (no geographic restriction) and IAM5 (the deploy role's object wildcard on the site bucket).
- Expected noise, not errors: synth warnings until a human acts (empty `lib/dns-records.ts`, Route 53 mode only; the `githubRepo` placeholder, both modes), Vitest's notice about its config file being ESM in a CommonJS package, npm's note about `fsevents` install scripts, and the CDK CLI printing "AI agent detected".
- CI's `infra` job (`.github/workflows/ci.yml`, in parallel with `check`, on every PR) runs `npm ci`, `npm run build`, `npm test`, `npx cdk synth -c dnsProvider=route53` and `npx cdk synth -c dnsProvider=external` in `infra/` (each mode named, so `cdk.json` recording the launch's DNS decision cannot drop one), with no AWS credentials and no `id-token` permission: synth needs neither (no context lookups; the account is left unset). Nothing in CI or in an agent session deploys it, and nothing in CI runs `cdk diff`.

## Deliberate house patterns

Settled decisions, not oversights.

- **Two languages, two prerendered pages, no runtime i18n library.** `/` and `/es` are separate files with separate heads (`<html lang>`, title, description, canonical, `og:locale`), and both list the full hreflang set plus `x-default`. The language is fixed per page by `LocaleContext`; switching is a plain link and a full page load. Do not propose `react-i18next`, browser-language detection or a client-side switch: crawlers must receive each language as its own indexable HTML, and an automatic redirect would hide the Spanish page from them.
- **Copy lives in typed modules, not JSON.** `SiteCopy` in `src/content/copy.ts` is the contract both languages implement, so a missing translation is a compile error. Localized data (partners, milestones, images) uses `Localized<T> = Record<Locale, T>`.
- **Static copies are checked, not generated.** `index.html` JSON-LD and `public/llms.txt` repeat facts from `src/content/` as literal text because crawlers read them without running JavaScript. `entity-graph.test.ts`, `llms.test.ts` and `site-dates.test.ts` hold them to the source. Do not propose replacing them with runtime injection.
- **Dates are spelled by hand.** `formatDate` in `src/content/news.ts` uses month-name arrays, not `Intl.DateTimeFormat`, because the page hydrates and two ICU builds need not spell a date identically. Do not "simplify" it.
- **The contact form validates in the page's language.** `noValidate` plus `validate()` in `src/lib/contactForm.ts`, because the browser's built-in messages speak the browser's language, not the page's. The `<form>` still says `method="post"`: before hydration the browser would otherwise submit a GET with every field in the URL (and CloudFront's logs); a POST to a page is refused at the edge. Delivery is honest: POST to `CONTACT_FORM_ENDPOINT` when set, otherwise hand a pre-filled `mailto:` to the visitor's email app; it never reports "sent" for a message that went nowhere. The hidden `website` field is a honeypot, and the endpoint applies the same rule. While a message is sending, the submit button is `aria-disabled`, not `disabled`: disabling the focused button drops keyboard and screen-reader focus to `<body>`, so a visitor whose send failed would lose their place on the page. A ref in `onSubmit` refuses a second submit (a click, or Enter in a field) until the first one settles. A mount effect reads the controls once after hydration and adopts what they hold: hydration keeps values the browser put there (typed on a slow load, or restored on reload or back/forward) while state starts empty, and the next re-render would otherwise wipe them. It runs after the hydration commit, so the first render still matches the served HTML.
- **"Partnership" hides below 360px in the header.** The mark, the EN/ES pill and the menu button do not fit beside the full wordmark on 320px phones, and overflowing made the page scroll sideways. The home link's `aria-label` keeps the full name.
- **Menu links close the dialog, then jump.** See `Navbar.tsx`; jumping with the scroll lock still on lands short of the section.
- **Partner logos are decorative (`alt=""`) on the cards** because the partner name is printed under each one, and the card's link is the name, stretched over the card with `::after`. The Powered By logos do carry alt text: there the logo is the only label.
- **Tailwind's default palette is off** (`--color-*: initial` in `src/index.css`). Brand colors only.
- **No external error tracking.** `ErrorBoundary` is local-only by design; a hosted tracker would also need a CSP change.
- **`CONTACT_EMAIL` is not displayed on the page.** The design shows none. It is the mailto target and the address in the failure message, and it equals `contactToAddress` in `infra/cdk.json` (`ContactForm.test.tsx` holds them together). Whether to publish an address is the partnership's decision (`docs/LAUNCH_CHECKLIST.md`).

### Hosting and deploy patterns

The full list, with reasons, is "Why it is built this way" in `infra/CLAUDE.md`. The ones reviewers most often question:

- **A strict CSP with no `'unsafe-inline'`, no nonces and no hashes.** Everything is same-origin and the HTML has no inline styles or executable scripts, so none are needed; a nonce would need a server rendering each response, which static S3 hosting does not have. Do not propose `style` props, CSS-in-JS that injects `<style>`, inline event handlers, or third-party fonts, scripts or images. `csp-compat.test.ts` enforces this on the built HTML.
- **The contact endpoint is a same-origin path, not an API.** `/api/contact` on the site's own CloudFront distribution, routed to a Lambda function URL with `AuthType: AWS_IAM` through Origin Access Control. Not API Gateway, not CORS, not the raw `lambda-url` hostname (the CSP and the IAM auth both refuse it). The browser's `x-amz-content-sha256` header is what OAC needs to sign a POST body, not a home-made auth scheme; do not remove it.
- **The Lambda never answers 404 and logs nothing a visitor typed.** The distribution maps every 404, `/api/*` included, to the HTML 404 page, so other `/api/*` paths get a JSON 400. Each request logs one JSON line: request id and outcome (plus invalid field names or an SDK error class name).
- **One error response, no SPA fallback.** 404 serves `/404.html` with status 404 and a 0-second TTL; 403 is deliberately unmapped (with OAC's LIST permission, a missing key is an honest 404, and the remaining 403s are WAF blocks that must not look like "page not found"). Do not propose mapping unknown paths to a 200 homepage.
- **Canonical URLs are enforced at the edge in one 301.** `infra/functions/canonical-host.js` sends the apex, uppercase document paths and trailing slashes to `https://www.oseptoledo.org` in a single hop; `src/paths.ts` mirrors it for dev and preview. The one documented difference (dotless `/assets/` paths, which no real file has) is tested in `infra/test/canonical-host.test.ts`.
- **Workflow actions are pinned to full commit SHAs** with the version in a trailing comment (`uses: actions/checkout@<sha> # v7.0.1`). The deploy job holds the OIDC token for the role that writes the site bucket, and ships what the build job produced, so a moved tag must not change what runs. Dependabot's `github-actions` updates bump the SHA and the comment together; do not "simplify" them back to `@v7`.
- **The deploy is two-phase and manifest-driven.** Upload without deleting, then the pages and metadata with short cache lifetimes, then invalidate and wait, then prune with `--delete`. Each extensionless page gets two exact excludes (`es`, `es.html`), never a prefix like `es*`; `api/*` is excluded from both syncs. The settings are repository variables, not secrets, so a job-level `if` can skip the jobs until they exist; never add `environment:` to either job (it changes the OIDC subject the deploy role trusts).
- **The deploy workflow is two jobs on purpose.** `build` (checkout with `persist-credentials: false`, `npm ci`, build, test; `contents: read` only) hands `dist/` and the route manifest to `deploy` as an artifact; `deploy` alone has `id-token: write` and runs no checkout, no npm and nothing from the artifact. Hundreds of third-party packages run during the build, and in a job with `id-token: write` any of them could request the OIDC token or plant a command on `PATH` for the credentialed steps. Do not merge the jobs, add npm or a checkout to `deploy`, or execute a file from the artifact there; permissions stay job-level (`permissions: {}` at the top).
- **CI checks `infra/` without AWS access, on purpose.** The `infra` job in `ci.yml` builds, tests and synthesizes on every pull request, Dependabot's and forks' included, so it runs code nobody has reviewed yet. It has `contents: read` only: no `id-token: write`, no `configure-aws-credentials`, no secrets. Do not propose adding them to run `cdk diff` in CI; the deploy role trusts `main` only, and a person runs the diff with `--profile osep-website` on the PR's branch, after `npm ci` in `infra/`, and pastes it into the PR.
- **Infrastructure is deployed by a person.** The deploy role can only write the site bucket and invalidate this distribution, and the workflow ignores `infra/**`. Until `githubRepo` is set, the role's trust policy carries an explicit Deny.
- **Deliberately absent:** an SNS email subscription in CDK (mail scanners click confirm and unsubscribe links; the runbook subscribes by CLI), reserved concurrency on the contact Lambda (new accounts' concurrency limit would fail the deploy, and it is not an abuse control: the WAF's per-IP limit stops bursts from one address, the `osep-website-contact-volume` alarm flags a slow flood, and SES production access, required before the form goes on, keeps one address's 120 an hour far below the daily sending quota; many addresses at once are out of scope), a site-wide cap on `/api/contact` (it would let one sender block the form for everyone, and no WAF rule is tight enough to protect the SES sandbox's 200 a day anyway; `infra/CLAUDE.md`), IPv6 (WAF counts every IPv6 address separately, so one host with a routed /64 could dodge the per-IP contact limit indefinitely; `enableIpv6: false` only drops the AAAA records, and since every CloudFront edge still accepts IPv6 for every distribution, the WAF's `BlockIpv6` rule is what refuses it, on every path; do not remove the rule or turn IPv6 on without a per-host bound that works over IPv6), real DNS records in `lib/dns-records.ts` (they must come from GoDaddy's zone export, not be invented), a post-deploy `curl` of the live site in `deploy.yml` (on the external DNS path the first content deploy runs before `www` points at CloudFront, so it would fail by design; the external uptime monitor in `docs/LAUNCH_CHECKLIST.md` catches a broken deploy within minutes), an SES configuration set or a bounce-forwarding mailbox (the `osep-website-ses-bounces` and `-ses-complaints` alarms watch SES's account-level metrics, which also count messages dropped for a suppressed inbox; `infra/CLAUDE.md`), and `lighthouse` as a required status check (its scores vary between runs; the ruleset requires `check` and `infra`, `infra/README.md` step 0.3).

## Conventions

- PR titles are plain imperative sentences with no Conventional Commit prefix (`Add the Spanish privacy notice`).
- Agents never merge, and never deploy or call AWS. Branch, review, merge and deploy rules: `CLAUDE.md`, `CONTRIBUTING.md` and `infra/CLAUDE.md`.
