# CLAUDE.md - infra

The AWS CDK app (TypeScript) for the Old South End Partnership website. Read the root [`CLAUDE.md`](../CLAUDE.md) first. This file is the inventory and the rules for agents working in `infra/`; [`README.md`](README.md) is the human launch runbook. Where either disagrees with `lib/`, the code wins; fix the doc in the same PR.

OSEP is an independent organization with its own AWS account (created with `admin@oseptoledo.org`, CLI profile `osep-website`), its own domain and its own GitHub repository. Nothing here depends on any other organization's AWS account, repository or tooling; provenance is recorded in [`THIRD_PARTY_NOTICES.md`](../THIRD_PARTY_NOTICES.md).

## Rules (non-negotiable)

- **Never deploy.** No `cdk deploy`, `cdk bootstrap`, `cdk destroy`, and no `cdk diff` or `aws` CLI call that uses credentials, unless a human has explicitly authorized that exact command in the current turn. The normal flow: an agent edits code, runs the credential-free checks below, and hands a human the exact commands, each with `--profile osep-website` and each inside `infra/` after `npm ci` there (the repository root has no `cdk.json` and no CDK CLI), saying where each one runs (README, Day to day):
  - **The review diff, before merge, on the PR's branch** (`gh pr checkout <N>`, or the author's own checkout): `npx cdk diff --profile osep-website`, pasted into the PR body. On `main` the change is not there yet, and without `npm ci` on the branch a CDK bump is not either, so a diff there shows nothing of it. It runs the branch's code with that person's AWS access, so they read the change first. (A Dependabot PR that changes only development dependencies other than `aws-cdk` needs none: README, Day to day, Monthly infra upkeep.)
  - **The deploy, after merge, on an up-to-date `main`** (`git switch main && git pull && cd infra && npm ci`, README, top of the runbook, so the CDK matches `main`'s lockfile): `npx cdk diff <Stack> --profile osep-website`, stopping on any removed `CarryOver` record (Gotchas, below), then `npx cdk deploy <Stack> --profile osep-website`.
- **Never put an account id, profile or AWS key in code or in an npm script.** The account comes from the `--profile` a human passes; `defineOsepStacks()` in `lib/website-stack.ts` reads `CDK_DEFAULT_ACCOUNT` and pins the region to `us-east-1`.
- **`lib/dns-records.ts` guards a live mailbox.** Never remove a record from `EXISTING_RECORDS` or change the zone's name servers without a human confirming the mail impact. The file's header explains why.
- **cdk-nag findings are fixed, or acknowledged next to the resource with a specific reason.** `test/nag.test.ts` fails on any unacknowledged finding and on any acknowledgment that no longer suppresses anything.

## Commands (all credential-free)

```bash
cd infra                                   # its own npm package; the root package.json knows nothing about it
npm ci
npm run build                              # tsc --noEmit
npm test                                   # vitest run (test/**/*.test.ts) && node --test test/*.node-test.mjs
npx cdk synth -c dnsProvider=route53       # both stacks
npx cdk synth -c dnsProvider=external      # OsepWebsiteStack only
```

Name the mode on both synths. A plain `npx cdk synth` takes `dnsProvider` from `cdk.json`, and once the launch records `external` there (README step 4) it would never build `OsepDnsStack`.

Node 24 (`nvm use` at the repo root). `cdk synth` needs no AWS access; if credentials happen to be in the environment the CLI may still look up the default account, so in automation run it with credentials unset. CI's `infra` job (`.github/workflows/ci.yml`) runs exactly these commands on every pull request, on a runner with no AWS credentials, no `id-token` permission and no secrets. The stacks make no context lookups, which is what lets that work: a `fromLookup` call would need credentials at synth time and fail the job. cdk-nag runs inside every synth (`bin/osep-website.ts`), so a finding fails `synth`, `diff` and `deploy` alike. Synth prints warnings by design until a human acts: the empty `dns-records.ts` (Route 53 mode only) and the `githubRepo` placeholder (both modes).

`aws-cdk-lib` is pinned exactly in `package.json` (a bump is always deliberate); the `aws-cdk` CLI is a caret range resolved in `package-lock.json`. Move them together: the CLI must read the cloud-assembly schema the library writes.

## Stacks

Both in `us-east-1`, both with termination protection, both built by `defineOsepStacks()` in `lib/website-stack.ts`, which the tests call too.

## Why it is built this way (settled; do not "fix")

- **OAC with LIST.** Without `s3:ListBucket`, S3 answers a missing key with 403, and the only way to show a 404 page would be to map 403, which also disguises WAF blocks. With LIST a missing key is an honest 404. CDK warns about listings on the origin; `defaultRootObject` is the mitigation and the warning is acknowledged in code.
- **One error response, no SPA fallback.** 404 serves `/404.html` with status 404 and TTL 0 (a mid-deploy 404 must not stick at the edge). Mapping unknown paths to a 200 homepage creates soft 404s. 403 stays unmapped. The mapping applies to `/api/*` too, which is why the Lambda never answers 404.
- **Bucket policy scoped by `AWS:SourceArn`** to this distribution, so no other CloudFront distribution, in any account, can read the bucket through OAC.
- **Canonical host in one hop.** Rules and reasons are in `functions/canonical-host.js`: document paths (not under `/assets/`, no dot in the last segment) are lowercased and lose every trailing slash in a loop, any other host 301s to the canonical one, the query string is rebuilt without re-encoding. `src/paths.ts` `normalizePath()` is the browser mirror; `test/canonical-host.test.ts` holds them together, including the one documented divergence (dotless `/assets/` paths, which are never real files or pages). The function also sends HSTS on its 301s.
- **The gated 4xx alarm.** A ratio over a quiet period is noise; the request gate makes small periods score 0. The 20% threshold is a starting point to revisit with real traffic.
- **Contact-form abuse: a per-IP WAF limit, a volume alarm, and SES production access; no global cap.** `ContactFormRateLimit` stops bursts from one IP address but not a script pacing itself under it (120 an hour per address). No WAF rule can hold that to the SES sandbox's 200 a day (WAF's tightest rate rule still allows ~1,400 a day per IP), and a site-wide `CONSTANT` rule would let one sender block the form for everyone. So the account leaves the sandbox before the form goes on (README step 8), where one address's 120 an hour is far below the daily quota, and `osep-website-contact-volume` flags a flood. Many addresses at once (a botnet, a proxy pool) are out of scope. Reserved concurrency and the Throttles alarm are not abuse controls.
- **IPv4 only: the WAF's `BlockIpv6` rule refuses IPv6, and `enableIpv6: false` publishes no AAAA records.** The per-IP limits bound one host only if one host is one address. WAF's rate rules key on a single source address and cannot group IPv6 addresses by prefix, so over IPv6 one host with a routed /64 (a common VPS default) could send each request from a new address, never reach `ContactFormRateLimit`, and spend the SES daily quota at SES's own send rate. `enableIpv6: false` alone does not prevent that: it only changes DNS (CloudFront stops answering AAAA queries for the distribution, and the zone publishes none). Every CloudFront edge still accepts IPv6 connections for every distribution and routes them by TLS server name and Host, so `curl --resolve www.oseptoledo.org:443:[<any CloudFront edge's IPv6 address>]` reaches this site over IPv6 anyway. `BlockIpv6` (priority 9, ahead of both rate limits, every path) blocks every request whose source is in the `WafIpv6Addresses` set, which is all of IPv6; README step 10 checks it on the live stack. No real visitor is refused: with no AAAA record no browser connects over IPv6, and IPv6-only mobile networks reach the site through their carrier's NAT64, over IPv4. The alternative, a count-all rule on `/api/contact`, is the site-wide cap ruled out above. Do not drop the rule, or turn IPv6 on, without a per-host bound that works over IPv6 first.
- **Retained, except after a failed first create.** Both buckets and the hosted zone use `RETAIN_ON_UPDATE_OR_DELETE`. With plain `RETAIN`, a first create that rolls back would leave empty buckets and a second `oseptoledo.org` zone behind. A stack whose first create failed still has termination protection on (the CDK CLI enables it before executing the change set), so a human must turn it off and delete the stack before retrying: README step 6, "If the first deploy of a stack fails".
- **No SNS subscription in CDK.** Mail scanners click SNS confirm and unsubscribe links. The README subscribes by CLI and confirms with `--authenticate-on-unsubscribe true`, which CloudFormation cannot set.
- **SES bounces and complaints: two alarms, no configuration set, no feedback forwarding.** SES accepts a send to an address on the account-level suppression list (on by default for bounces and complaints) and drops it, counting a `Bounce`, so the form answers "sent" for a message that never arrives and none of the contact alarms see it. Alarms on SES's free account-level `Bounce` and `Complaint` metrics catch that, and fire again on each later dropped message. The cost is a false alarm per message while the inbox has an automatic reply on, which some providers send to SES's return address and SES counts as a soft bounce; the runbook and the checklist's "Who receives messages" cover that. A configuration set with an SNS event destination would add parts for the same signal, and forwarding bounce notices (`FeedbackForwardingEmailAddress`, or a `no-reply@` mailbox) would send them to the very inbox that bounced.
- **The contact rate limit matches the decoded path.** CloudFront picks the `/api/*` behavior from a normalized path but forwards the raw one, and WAF sees the raw one too. So `ContactFormRateLimit`'s scope-down applies `URL_DECODE`, `NORMALIZE_PATH` and `LOWERCASE` before matching `/api/contact`: `/api/%63ontact`, `/api//contact` or `/API/Contact` cannot get the site-wide limit instead of the contact one. The Lambda also serves only the exact raw path (`CONTACT_PATH` in `contact.mjs`); README step 10 checks on the live stack that an encoded path is refused.
- **The core rule set's 8 KB body rule counts instead of blocking.** `SizeRestrictions_BODY` would answer every body over 8,192 bytes with WAF's plain 403, which looks like an Origin rejection or a rate-limit block, and the contact endpoint's documented `413 too_large` (same cap, `MAX_BODY_BYTES`) would never reach a visitor. Only `/api/*` accepts a body (the default behavior is GET/HEAD), and the Lambda refuses an oversize one before parsing it.
- **The contact form is same-origin.** `/api/*` on the site's own distribution, so `connect-src 'self'` covers it and no CORS exists. OAC requires the browser to send `x-amz-content-sha256` (SHA-256 of the body) on POST; requests without it are refused by Lambda before the function runs.
- **No managed policies.** The Lambda role is hand-written (its own log group, one SES action); the OIDC provider is the native resource, not a custom-resource Lambda.

## What is not in these stacks

- **The AWS account, IAM Identity Center users and the `osep-website` CLI profile**: created by hand (README step 1).
- **CDK bootstrap**: once per account, by a human.
- **Domain registration**: stays at GoDaddy. On the external path all DNS records do too.
- **The SNS email subscriptions**: CLI, one per address the launch checklist's "Who receives alarm emails" names, README step 9.
- **Uptime monitoring**: an external HTTPS monitor set up by hand (`docs/LAUNCH_CHECKLIST.md`, Uptime monitor). The CloudWatch alarms need traffic that reaches CloudFront, so they cannot see an unreachable site (a lapsed domain, broken DNS, an expired certificate), and the 4xx alarm ignores periods with fewer than 50 requests.
- **The SES sandbox exit** (production access): requested by hand in the SES console, and required before the form goes on (README step 8). The sandbox's 200-a-day quota is shared by every visitor, so one script could use it up.
- **GitHub repository variables** `AWS_ROLE_ARN`, `S3_BUCKET_NAME`, `CLOUDFRONT_DISTRIBUTION_ID`: set from the outputs (README step 7, straight after the first stack deploy), read by `.github/workflows/deploy.yml`, which deploys content only and ignores `infra/**`.
- **`CONTACT_FORM_ENDPOINT`** in `src/constants/contact.ts`: flipped to `/api/contact` by a site PR (README step 11) only once SES is verified with DKIM `SUCCESS` and out of the sandbox (step 8) and the smoke tests pass (step 10).

## Gotchas

- **CI builds, tests and synthesizes `infra/`, but cannot diff it.** The `infra` job has no AWS access, so a green run says nothing about what a deploy would change. Run the commands above before every infra PR anyway, and have a person run `npx cdk diff --profile osep-website` on the PR's branch, inside `infra/` after `npm ci` there, and paste it into the PR body (Rules, above; README, Day to day). A diff run on `main`, or on the branch with an old install, compares the wrong templates and shows nothing of the change.
- **The distribution domain is not a smoke-test URL.** It 301s to `www` like any non-canonical host. To reach the distribution before DNS points at it: `curl --resolve www.oseptoledo.org:443:<edge IP from dig of the distribution domain> https://www.oseptoledo.org/`.
- **Changing the CSP** means editing `CONTENT_SECURITY_POLICY`, the literal in `test/website-stack.test.ts` and `src/__tests__/csp-compat.test.ts` together, and deploying the stack alongside the site change. Any inline `style=""` or executable inline script in the built HTML is blocked in production but invisible locally.
- **`dnsProvider` and `githubRepo` must be the same on every deploy.** Deploying once with `-c dnsProvider=external` and later without it would try to move to Route 53. `githubRepo` changes only if the repository is transferred or renamed, and then the deploy role refuses every token until it is redeployed with the new name (README, Day to day). Keep the real values in `cdk.json` (only there: `DEFAULT_CONTEXT` in `lib/config.ts` keeps the defaults, and `test/config.test.ts` accepts any valid value for these two keys in `cdk.json`).
- **Deploy from an up-to-date `main`, and read the `OsepDnsStack` part of the diff.** `cdk deploy OsepWebsiteStack` deploys `OsepDnsStack` first whenever its template differs, so a checkout whose `lib/dns-records.ts` lacks the carried-over records deletes them from the live zone. A `[-] AWS::Route53::RecordSet` line with `CarryOver` in its name means stop (README step 6). Say so whenever you hand a human a deploy command.
- **Contract strings shared with other files**: `CONTACT_ENDPOINT_PATH` (`/api/contact`) with the site and the Lambda; the Lambda's env var names and its 500 outcomes; the output names with `deploy.yml` and the README. Change them together.
- **Vitest prints a `configLoader: 'native'` notice** about `vitest.config.ts` being ESM syntax in a CommonJS package. It is informational; the package stays CommonJS because `cdk.json` runs the app through ts-node.
